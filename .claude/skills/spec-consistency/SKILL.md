# 명세 자기일관성 전수 검사

## 왜 필요한가

G0-23 이 실제 사고다. `Cogito++_구현명세서.md` §3-1 CCJ-5 에는
"지수 자릿수의 선행 0 제거 (예: `1.5e-7`)" 라고 쓰고,
§3-1-a 규범 골든 표에는 `1e-07` 을 박아뒀다. 3,100행 문서에서
**규칙과 그 규칙의 예시가 어긋난 것을 작성자 본인이 못 잡았다.**

이 스킬은 그 실패를 기계적으로 반복 검사한다.

## 검사 클래스 6종

### C1. 규칙 ↔ 예시 불일치
서술된 규칙을 그 문서 안의 예시·표·코드블록에 **직접 적용**해 본다.

- 골든 벡터 표의 각 행이 서술된 규칙과 일치하는가
- 코드 예시가 바로 위 문단의 규범을 따르는가
- 스키마 예시가 그 스키마의 허용 키워드 목록 안에 있는가

### C2. 같은 개념의 두 정의
같은 이름이 두 곳에서 다르게 정의되는가.

- 함수 시그니처가 여러 절에 다르게 나오는가 (예: ABI v1.0 vs v1.1)
- 같은 절차가 두 곳에 다른 순서로 적혔는가
- enum 값 집합이 절마다 다른가

### C3. 절차 충돌
두 절이 같은 동작을 서로 다르게 규정하는가.

- 상태 전이표 ↔ 산문으로 쓴 절차
- 커밋 순서 ↔ 단계 번호
- FSM 재진입 ↔ 함수 내부 루프

### C4. 끊어진 참조
- `§N-M` 참조가 실제로 존재하는가
- 표에서 "§X 참조"라 했는데 §X 에 그 내용이 없는가
- 다른 문서의 절을 참조하는데 그 문서에 없는가

### C5. 계약 구멍
어떤 절이 요구한 값을 다른 절의 계약이 제공하지 않는가.

- UI 가 표시하라는 필드가 페이로드 정의에 없는가
- 테스트가 검증하라는 동작의 규범 조항이 있는가
- 시작 실패 조건이 "기준보다 낮으면"처럼 미정의 값을 참조하는가

### C6. 물리적 파일 무결성
- 원시 제어문자(U+0000~U+001F, `\t\n\r` 제외)가 텍스트에 들어갔는가
- 코드펜스(```) 개수가 짝수인가
- 표의 열 개수가 헤더와 일치하는가
- mermaid 블록이 닫혔는가

## 절차

1. **대상 범위를 정한다.** 인자가 없으면 `Cogito++_구현명세서.md` 전체.
2. **먼저 구조를 뽑는다** — 절 목록, 표 개수, 코드블록 개수, 파일 크기.
   C6 는 여기서 스크립트로 즉시 판정한다.
3. **규범 문장을 수집한다.** "…해야 한다", "…한다", "…금지한다", "MUST/SHOULD" 형태.
4. **각 규범마다 그 문서 안의 적용 사례를 찾아 대조한다.** 샘플링하지 않는다.
5. **교차 문서 대조**는 `spec-auditor` 서브에이전트에 위임한다 (축 C).

## 보고 형식

```markdown
## 명세 자기일관성 검사 결과

**대상**: 파일명, N행, M바이트, 절 X개
**검사 클래스**: C1~C6

### 발견 (심각도 순)

#### [C1] 한 줄 요약
- 규칙: §A — "원문"
- 적용 사례: §B — "원문"
- 어느 쪽이 규범인지 판정 필요: (근거)
- 고치는 쪽 제안:

### 검사했으나 문제없음
- C4 절 참조 N개 전수 확인
- C6 제어문자 0, 코드펜스 짝수

### 검사하지 못한 범위
(전수하지 못했다면 반드시 명시)
```

## 규칙

- **전수 검사다.** "몇 개 확인했다"로 끝내면 G0-23 이 또 통과한다.
- 발견을 **심각도 순**으로 정렬한다. C2/C3(두 정의·절차 충돌)이 가장 위험하다 —
  구현자가 어느 쪽을 따를지 임의 선택하게 된다.
- 어느 쪽이 맞는지 **단정하지 않는다.** 권위 판정은 사람의 몫이다.
  다만 권고안은 낸다.
- 승인 없이 명세 본문을 고치지 않는다. C6(파일 무결성)만 예외적으로 즉시 수정 제안한다.
