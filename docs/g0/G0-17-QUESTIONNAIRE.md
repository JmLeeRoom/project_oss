## D-1. 인증원과 `auth.mode`

### 질문

**첫 배포 라인에서 운영자를 인증하는 1차 수단은 무엇인가? `http_server.auth.mode` 에 들어갈 값 하나와, `accepted_auth_methods` 에 남길 값 목록을 지정하라.**

### 왜 필요한가

- `Cogito++_구현명세서.md:2802-2803` — `auth.mode` 와 `accepted_auth_methods` 는 config 필수 항목이다. 명세의 `"mtls"` / `["mtls","badge","oidc"]` 는 **예시 config 값**이다.
- `Cogito++_구현명세서.md:2171` — "`auth_method` 가 config `auth.accepted_auth_methods` allowlist 에 없으면 `COGITO_ERR_INVALID_ARG`." 즉 이 목록이 비거나 틀리면 **모든 요청이 ABI 진입에서 거부**된다.
- `Cogito++_구현명세서.md:2172` — "주체는 인증된 세션에서만 유도한다. 요청 본문·쿼리스트링·클라이언트가 보낸 헤더의 신원 값을 그대로 사용하는 것을 금지한다." → 인증원이 정해지지 않으면 **주체를 만들 방법 자체가 없다.**
- `Cogito++_개발_작업체크리스트.md:1366` — "mTLS/badge/OIDC claim 을 stable subject/roles/auth method/line ID 로 server-side map 한다." 매핑 규칙은 인증원별로 완전히 다르다.
- `Cogito++_구현명세서.md:2594` — "**`tests/web/auth` 가 통과하기 전에는 UI 를 만들지 않는다**."

### 선택지와 트레이드오프

| 선택지 | 얻는 것 | 포기하는 것 |
| --- | --- | --- |
| ◆ (a) mTLS 클라이언트 인증서 | 폐쇄망에서 외부 IdP 의존 0. 전송 계층에서 신원이 끝남 | **인증서 = 기계**이지 사람이 아니다. 한 패널 PC 를 교대 근무자 여럿이 쓰면 D-3 의 개인 귀속이 무너진다. 발급·폐기(CRL/OCSP) 운영이 별도 부담 |
| (b) 사원 배지 리더 | 교대 근무자 개인 귀속이 자연스럽다. 현장 동선과 일치 | 리더 하드웨어·드라이버 의존. 배지 대여·도난 시 귀속이 거짓이 된다. 리더 고장 시 대체 경로 필요 |
| (c) 사내 OIDC | 기존 계정·역할 체계 재사용. 계정 폐기가 중앙에서 즉시 반영 | **IdP 도달성이 OT 세그먼트 가용성에 종속**된다(D-5 와 충돌 가능). IdP 장애 = 승인 불가 |
| (d) (a)+(b) 조합 — 기계 인증서로 단말을, 배지로 사람을 | 단말과 사람을 분리해 둘 다 감사에 남긴다 | 구현·운영 표면이 가장 크다. bootstrap 경로가 2개 |

**Claude 가 정할 수 없는 이유**: 현장에 배지 리더가 있는지, 사내 IdP 가 OT 세그먼트에서 보이는지, 인증서 발급 체계가 있는지는 문서에 없다. 추정하면 `CLAUDE.md:41-45` 가 지목한 "지어내기" 실패다.

## D-2. step-up 재인증 수단과 TTL

### 질문

**승인·거절·봉인·ack·finalize 재시도에 요구할 step-up 재인증 수단은 무엇이고, 한 번의 step-up 이 유효한 시간은 몇 초인가?**

### 왜 필요한가

- `Cogito++_구현명세서.md:2645` (W11) — "승인·거절·봉인·잠금해제는 **step-up 재인증**을 추가로 요구한다. 세션 쿠키만으로 PLC 쓰기가 승인되면 안 된다."
- `Cogito++_구현명세서.md:2806-2807` — `step_up.required_for` 5개 경로와 `methods` / `ttl_ms` 가 config 항목이다. 명세의 `["badge","pin","mtls"]` 와 `120000` 은 **예시값**이다.
- `Cogito++_구현명세서.md:2760-2768` — POST 7경로 중 5경로에 step-up ✅ 표시가 있다.
- `Cogito++_개발_작업체크리스트.md:1381-1382` — "step-up 실패 시 nonce 소비, queue 제출, state change 가 0회인지 확인한다." 이 테스트는 step-up 수단이 정해져야 작성된다.

### 선택지와 트레이드오프

| 선택지 | 얻는 것 | 포기하는 것 |
| --- | --- | --- |
| (a) 배지 재탭 | 물리적 현장성. 대리 승인이 어렵다 | 리더 앞으로 이동해야 함 — 긴급 상황 지연 |
| ◆ (b) PIN 재입력 | 하드웨어 무관. 장갑 착용 시에도 가능(§12-12 터치 타깃 규범과 정합) | PIN 공유·어깨너머 관찰. PIN 저장·검증 경로가 새 비밀 관리 표면 |
| (c) mTLS 재핸드셰이크 | 새 비밀 저장소 없음 | 브라우저 UX 가 통제 불가에 가깝고, 같은 인증서라 "사람 재확인" 의미가 약하다 |
| (d) step-up 생략 | 구현 최소 | **W11 위반.** 세션 탈취 1회가 설비 쓰기 승인으로 직결된다. 이 선택지를 고르면 W11 을 명세에서 삭제하는 결정을 함께 서명해야 한다 |

TTL 트레이드오프: 짧을수록 재인증 빈도가 올라 교대 현장에서 승인 지연이 생기고, 길수록 자리 비움 중 승인 위험이 커진다. **연속 승인이 흔한지 여부는 현장 데이터이므로 Claude 가 정할 수 없다.**

## D-3. 역할 이름 목록과 명령별 권한 행렬

### 질문

**이 제품이 인식할 역할 이름을 전부 열거하라. 그리고 7개 POST 명령 각각을 어느 역할이 실행할 수 있는지 표를 채워라.**

### 왜 필요한가

- `Cogito++_구현명세서.md:2752` — "`turn_begin` payload 에 `requester_subject_id`·`requester_roles`·`requester_auth_method` 를 **필수로 기록**한다." → **역할 문자열이 감사 본문에 그대로 들어간다.** 나중에 이름을 바꿔도 과거 기록은 옛 이름으로 남는다.
- `Cogito++_구현명세서.md:719`, `:758`, `:2047`, `:2163` — `roles` / `roles_csv` 가 Subject·정책 규칙·ABI 구조체에 걸쳐 있다. `"operator"`, `"qa_engineer"`, `"viewer"` 는 **명세의 예시 문자열**(`:1823`, `:1829`)이지 승인된 역할 체계가 아니다.
- `Cogito++_구현명세서.md:2497` — `core/gate` 테스트가 "4 모드 × 역할 × effect/risk 행렬"을 요구한다. 역할 집합이 없으면 이 행렬을 만들 수 없다.
- `Cogito++_구현명세서.md:324` — `role_denied` reason_code 가 이미 존재한다. 어떤 조합에서 이 코드가 나오는지가 D-3 의 답이다.
- `Cogito++_개발_작업체크리스트.md:1375` — "command 별 role matrix 를 만들고 queue 제출 전에 403 으로 거부한다."
- `Cogito++_구현_요구사항.md:700` — "사용자 인증원, **역할 체계**, 승인 분리 원칙"은 제품 책임자 확정 사항이다.

## D-4. 승인 분리(SOD) 예외를 둘 것인가

### 질문

**요청자와 승인자가 같은 사람인 승인을 허용할 상황이 있는가? 있다면 어떤 조건에서, 무엇을 감사에 남기고 허용하는가? (`approval.allow_self_approval` 의 값)**

### 왜 필요한가

- `Cogito++_구현명세서.md:2194` — "코어는 `approver->subject_id == requester_subject_id` 이고 `effect != none` 이면 거부한다. `reason_code = approval_self_approval`. config `approval.allow_self_approval` 로만 완화 가능하며, **완화 사실 자체를 `turn_begin` 에 감사한다.**"
- `Cogito++_구현명세서.md:2646` (W12) — "요구사항 §16 '승인 분리 원칙'의 최소 구현"
- `Cogito++_구현명세서.md:2812` — `"approval": { "allow_self_approval": false }` 는 **예시 config 값**이다.
- `Cogito++_개발_작업체크리스트.md:89` — G0-17 이 명시적으로 "SOD 예외"를 미결로 지목한다.

- `Cogito++_개발_작업체크리스트.md:1762` — "보안 책임자가 auth/CSRF/**SOD**/TLS/CSP/audit read/secret 증거를 서명한다."

### 선택지와 트레이드오프

| 선택지 | 얻는 것 | 포기하는 것 |
| --- | --- | --- |
| ◆ (a) 예외 없음 — `allow_self_approval: false` 고정 | 승인 분리가 코드로 강제된다. 감사 해석이 단순 | **1인 야간 교대에서 설비 변경이 불가능**해진다. 현장이 이를 우회하려 계정 공유를 하면 오히려 귀속이 완전히 붕괴한다 |

| (d) 예외 없음 + 원격 2인 승인 절차 | 분리 유지 + 야간 운영 가능 | 원격 승인자의 상시 가용성이 필요. D-5 의 네트워크 범위와 충돌할 수 있다(원격 접근 = OT 경계 확장) |

## D-5. 도달 네트워크 범위와 OT/IT 경계 정책

### 질문

### 왜 필요한가

- `Cogito++_구현명세서.md:3004` — "호스트는 OT 세그먼트에 바인드한다. OT/IT 경계를 넘어 노출하려면 별도 검토를 문서화한다. `origin_allowlist` 에 IT 대역 출처를 넣지 않는다."

## D-7. 기준 해상도

### 질문

**승인 화면 레이아웃을 검증할 기준 해상도(가로×세로 CSS px)는 무엇인가? 복수 해상도가 있으면 전부 열거하고 그중 최소 기준을 지정하라.**

### 왜 필요한가

- `Cogito++_구현명세서.md:2999` — "산업용 패널은 1024×768·1280×800 이 흔하다. §12-8 A-1 의 권위 영역은 **1024×768 에서 스크롤 없이 전부 보여야 한다**." (이 문장은 명세의 서술이며, 현장 실제 해상도는 미결이다)
- `Cogito++_구현명세서.md:2866-2870` (A-1) — 권위 영역은 화면 상단 고정, 스크롤·접기 없음이며 렌더링할 필드가 11개다: `tool_name`·`effect`·`risk`·`grammar_coverage`·`approval_required`·CCJ 정규화 `arguments`·`before`·`policy_rule_id`·`action_digest` 앞 16자리·잔여 만료 시간·`requester_subject_id`.
- `Cogito++_구현명세서.md:3000` — "승인·거절 버튼의 터치 타깃 최소 56×56 CSS px, 상호 간격 최소 24 px" + `:2877`(A-5) "최소 24px 분리 + 승인은 2단계 확인". **이 제약과 11개 필드가 동시에 최소 해상도 안에 들어가야 한다** — 여유가 없다.

이 문서는 번들 크기·메모리 추정치를 쓰지 않는다(`Cogito++_구현명세서.md` 부록 A 마지막 항목: "프론트엔드 번들·메모리 추정치 — 대상 패널 PC 실측 후에만 기재").

### 선택지와 트레이드오프

| 선택지 | 얻는 것 | 포기하는 것 |
| --- | --- | --- |
| (a) 명세가 서술한 1024×768 을 기준으로 삼는다 | 가장 좁은 조건에서 A-1 을 만족시키면 상위 해상도는 자동 충족 | 정보 밀도를 크게 낮춰야 한다. 보조 정보(대화·감사표)가 항상 스크롤 아래로 밀린다 |
| (b) 현장 실측 최소값을 기준으로 삼는다 | 실제 장비에 맞는 최적 레이아웃 | 장비 교체 시 재검증 |
